# AI Studio — Claude Code / Codex 협업 가이드

> 적용 범위: AI Studio 전체 개발 단계(T01~T10). 기존 승인 ADR 및 AGENTS.md의 안전 규칙을 대체하지 않는다. 사용자 승인 후 저장소에 반영한다.

## 1. 역할

| 담당 | 책임 |
|---|---|
| 사용자 | 요구사항, 작업 배정, 실제 사용자 검증, 최종 승인 및 병합 결정 |
| ChatGPT | 아키텍처·DB·API 설계 검토, ADR 제안 및 검토 |
| Claude Code | 승인된 범위의 설계 구체화, 기능 구현, 테스트, 코드 리뷰 |
| Codex | Claude Code와 동등한 구현·테스트·리뷰 역할. 배정된 범위만 작업 |

두 개발 에이전트 모두 설계를 임의 변경하지 않는다. 사용자가 승인한 작업 범위와 ADR을 따른다. 구현 담당자와 독립 검토 담당자는 가능하면 분리한다.

## 2. 세션 시작

1. 저장소 루트의 `AGENTS.md`, `CLAUDE.md`, `STATE.md`, `DECISIONS.md`, 이 문서 및 `TASKS.md`를 읽는다. TASKS.md가 없으면 사용자 배정과 STATE.md를 기준으로 한다.
2. 해당 단계의 `docs/plans/`, `docs/design/`, `docs/reports/` 문서와 필요한 API 계약을 읽는다.
3. `git status --short`, `git branch --show-current`, `git log -5 --oneline`으로 현재 작업 위치를 확인한다. 원격 상태는 `git fetch origin`으로 확인한다.
4. 담당 작업 ID, 기준 커밋, 수정 허용 경로, 선행 조건, 테스트 계획을 확인한다. 배정되지 않은 변경이나 충돌이 있으면 사용자에게 보고한다.
5. 이전 작업을 중복 구현하지 않는다. 문서와 코드가 충돌하면 근거와 영향 범위를 보고하고 승인되지 않은 설계 변경은 보류한다.

## 3. 협업 방식

### 교대 개발 (기본)

한 작업 브랜치에 한 번에 한 명만 구현한다. 사용량 제한 또는 PC 이동 시 기존 담당자는 작업 상태를 기록하고 사용자 승인 범위에서 WIP 커밋·푸시한다. 다음 담당자는 커밋과 인수인계를 읽고 미완료 작업부터 재개한다. 이전 담당자가 작업을 중단했음을 확인하기 전에는 같은 작업 트리를 수정하지 않는다.

### 병렬 개발 (선택)

공통 DB/API/인터페이스를 먼저 확정하고 수정 경로가 겹치지 않는 작업으로 나눈다. 각 에이전트는 별도 브랜치 및 별도 Git worktree를 사용한다. 공유 `.env`, DB, 포트, 생성 파일, lockfile의 충돌에도 주의한다. 공통 파일(ADR, STATE, TASKS, OpenAPI, 빌드 설정 등)은 지정된 통합 담당자만 갱신하거나 별도 변경 제안으로 제출한다.

### 독립 리뷰

리뷰 담당자는 지정된 커밋을 기준으로 읽기 전용 검토를 한다. 구현자가 작업 중인 파일을 수정하지 않는다. 결함 수정은 별도 배정 후 진행한다. 리뷰 결과는 `docs/reviews/`에 저장하거나 사용자에게 전달한다.

## 4. Git 및 데이터 안전 규칙

- `main` 직접 개발·푸시·병합 금지(사용자가 명시 승인한 경우 제외).
- 다른 담당자의 변경을 덮어쓰거나 `reset --hard`, 강제 푸시, 무단 stash/checkout/clean을 수행하지 않는다.
- 작업 브랜치 커밋·푸시는 승인 범위 내에서만 수행한다. 스테이징 대상을 확인하고 비밀정보 및 빌드 결과물을 제외한다.
- 이미 적용된 Flyway migration은 수정하지 않는다. 필요 시 신규 migration 및 ADR을 제안한다.
- 작업 DB와 업무 DB를 통합 테스트 대상으로 사용하지 않는다. 테스트는 격리된 Testcontainers 또는 별도 임시 MariaDB를 사용한다. `docs/guides/LOCAL_TEST_GUIDE.md`를 따른다.
- `.env`, 비밀번호, 토큰, DB dump, 생성 미디어는 Git에 넣지 않는다. 다른 프로젝트의 환경변수를 수정하지 않는다.
- 실제 유료 API 호출, 지출 허용, YouTube 업로드, 운영 계정 생성은 별도 사용자 승인 전 금지한다.

## 5. 작업 완료 기준

단위·통합 테스트, OpenAPI 계약, 생성 타입 검사, 프론트 lint/typecheck/test/build, 비밀정보 검사 등 변경 범위에 맞는 검증을 수행한다. 실제 빌드 산출물과 사용자 실행 경로도 확인한다. 미실행 테스트는 통과로 기록하지 않는다. 기존 검증을 우회하거나 실패 테스트를 숨기지 않는다.

작업자는 구현 완료 시 `IMPLEMENTED`로 보고한다. 최신 PR HEAD의 CI, 독립 리뷰, 필요한 사용자 실행 검증 및 최종 승인 후에만 `DONE`으로 전환한다. 다음 단계 착수와 main 병합은 별도 승인 사항이다.

## 6. 인수인계 형식

`STATE.md` 또는 지정된 작업 보고서에 다음을 기록한다.

- 작업 ID / 담당 / 상태 / 브랜치 / 기준 및 마지막 커밋
- 완료한 기능과 변경 파일
- 미완료 기능 및 정확한 다음 작업
- 실행 명령과 실제 테스트 결과, 실패·미검증 항목
- 적용된 Flyway 버전과 DB 변경 여부(PC별 구분)
- 추가 설계 결정 및 승인 대기 항목
- 푸시·PR·CI 결과 및 남은 검증
- 필요한 환경변수 이름(값 제외)

## 7. 독립 리뷰 보고서 형식

`docs/reviews/<작업ID>_CODEX_REVIEW.md` 또는 `<작업ID>_CLAUDE_REVIEW.md` 사용.

각 발견 사항에는 ID, 심각도(CRITICAL/HIGH/MEDIUM/LOW), 파일:줄, 관련 ADR, 발생 조건, 영향, 재현 방법, 수정 제안, 검증 근거를 기록한다. 확인된 결함과 개선 제안을 구분한다. 실제 코드나 로그를 확인하지 못한 사항은 명시한다. 문제가 없다면 검토 범위와 남은 위험을 기록한다.

## 8. 현재 적용 제안 — T02

- Claude Code: 승인된 T02 UI 개선 및 디자인 시스템 구현.
- Codex: 지정된 T02 백엔드 커밋의 독립 리뷰(인증, CLI, CSRF, rate limit, DB 보호, 예산 Fail Closed, 원장, 동시성, 환율, 권한, 계약 테스트, gitleaks 개별 예외).
- Codex는 이번 리뷰에서 제품 코드를 수정하지 않는다. 리뷰 결과를 받은 후 수정 작업을 별도로 배정한다.
- 기존 Draft PR #1은 최종 승인 전 병합하지 않는다. T03는 시작하지 않는다.
- 실제 브랜치/커밋/진행 상태는 작업 시작 시 STATE.md 및 Git으로 재확인한다.

