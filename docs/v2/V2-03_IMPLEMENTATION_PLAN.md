## 1. 목표와 경계

한 명의 운영자가 선택한 소재, 또는 자동 선정한 소재로 재미와 설명 가치가 있는 IFNOVA 영어 Shorts(40~60초)의 조사 기록, 내레이션, 장면별 미디어 제작 입력을 만든다. 기존 고정 단계 순서 `SELECT → RESEARCH → SCRIPT → SCENES → IMAGE`를 유지한다. V2-03은 타입 계약·FAKE·오프라인 fixture로 검증한다. 실제 음성 길이·자막 싱크와 미디어·MP4는 V2-04에서 다룬다. 실제 유료 검색·AI·의미 검증 공급자 연결, 자동 유료 재작성, 최종 75점 기준과 최대 2회 부분 개선은 V2-05에서 별도 승인 후 진행한다. 재발굴, 범용 워크플로우, 대본·타임라인 편집기, 관리자 기능은 제외한다.

## 3. 단계 공통 계약

요청 ID, 연결 Run·Revision ID와 Revision 해시, 확정 선정 지문과 후보 ID·DISCOVER 응답 해시를 사용한다. 후보는 같은 요청에서 이미 적용된 DISCOVER와 확정 SELECT 기록을 구조화해 읽는다. 최초/최신 평가 및 선택 증거는 그대로 추적한다. 후보의 evidence ID는 조사 단서로만 전달한다. 기존 평가에서 차단하는 사실 단정은 SELECT에서 계속 차단한다. 질문 또는 검증 계획으로 표현된 미확인 내용은 RESEARCH에서 조사 과제로 기록한다.

언어는 연결 Revision 및 제작 요청의 고정 언어와 일치시킨다. 채널 스타일은 요청이 참조하는 `channel_config_id`의 해당 버전에서 필요한 설명 전략·대상 시청자·시각/톤 설정만 추출한다. 실제 구현 전 설정 버전의 불변성과 스타일 필드 위치를 확인한다. 편집 가능한 채널 값에만 필요한 필드가 있으면 신규 요청 생성 시 필요한 값만 고정하는 변경을 별도 승인받는다. 각 단계는 계약·프롬프트·검증 규칙·공급자 버전과 이전 단계 본문 해시를 포함한 고정 입력을 사용한다. 가변 카탈로그나 현재 설정으로 재시작 입력을 재구성하지 않는다.

### RESEARCH — R01·R02

Shorts의 핵심 설명에 필요한 사실부터 조사한다. 초기 권장 범위는 검색어 2~4개, 출처 후보 3~8개, 핵심 사실 2~5개, 활용 출처 1~5개다. 운영 참고값으로 사용하며 최소 개수를 강제하지 않는다. 공신력 있는 단일 출처로 주장을 충분히 확인할 수 있으면 추가 검색을 요구하지 않는다.

- 입력: 핵심 질문·설명 관점·후보 구성·조사 계획, 미검증 주장, 대상 채널 스냅샷. 후보에서 명시하지 않은 가설·가상 전제는 질문과 관점을 바탕으로 정리하며 출처가 검증된 사실로 승격하지 않는다.
- 출력: `question`, `angle`, `investigations[{id, question, requestedEvidence, status}]`, `claims[{id, kind, text, evidenceRefs, uncertainty}]`, `sources`, `limitations[]`, `scriptClaimIds[]`. 주장 유형은 `FACT`, `HYPOTHESIS`, `SCENARIO`, `UNVERIFIED`로 둔다. 가상 시나리오는 전제와 적용 한계를, 가설은 추론 근거와 불확실성을 기록한다.
- 출처는 `id, origin, status, url, title, publisher, checkedAt, documentHash`로 식별한다. 주장 연결은 `sourceId, locator, supportingExcerpt, relation`을 남긴다. 인용은 근거 확인에 필요한 짧은 부분만 보존하며 상충 자료는 반대 근거로 표시한다.
- 출처 조회 상태와 주장 지지 판정을 별도로 기록한다. `VERIFIED`는 신뢰 경계에서 실제 문서를 조회하고 식별한 출처에만 부여한다. 사실로 채택하려면 해당 수치·단위·맥락에 대한 별도의 `SUPPORTS` 판정도 필요하다. `CONTRADICTS`나 `INSUFFICIENT`는 지지로 집계하지 않는다. 모델이 반환한 URL·인용·검증 플래그는 조사 단서로 저장할 수 있다. 조회 실패·상충·검증 부족을 명시하며 FAKE와 FIXTURE는 `VERIFIED`로 승격할 수 없다.
- 핵심 설명에 필요한 근거가 부족하면 저장 가능한 조사 결과와 지적을 남기고 SCRIPT를 차단한다. 선택적 미확인 항목은 대본에서 제외할 수 있다. 가상 전제와 추론은 시청자가 알아들을 수 있게 표현한다.

### SCRIPT — R03·R04

- 입력: 채택된 RESEARCH 해시와 핵심 정보, 조회된 근거, 질문·관점, 언어·스타일, 목표 길이, 고정된 최근 대본 비교 입력. 같은 채널의 최근 채택 대본과 V2-02 유사 콘텐츠 참조를 소량 사용한다. 비교 대상 ID·해시와 정규화한 요약을 첫 발송 전에 고정한다. 초기 카탈로그가 비어 있으면 비교 이력이 없음을 표시한다.
- 출력: `language`, `segments[{id, narration, claimIds}]`, `hookSegmentIds`, `estimatedDurationMs`, `timingRuleVersion`, `editorialIntent`(차별적 설명 가치와 결말 의도), 검수 지적 목록. 내레이션의 숫자·비교·인과 표현과 RESEARCH 주장·근거의 의미가 일치해야 한다. 사실 외에도 가상·추론에 해당하는 문장을 연결해 검수 가능하게 한다.
- 재미·설명 가치·독창성·시청 지속률을 함께 고려한다. 첫 3초의 Hook, 가상 상황과 과학적 설명의 연결, 기억에 남는 결말을 권장한다. 소재에 따라 시간 경과형, 결과 예측형, 비교형, 반전형, 몰입형, 다큐멘터리형을 활용하거나 조합한다. 문장 패턴·시간 배분·전개 순서는 소재에 맡기며 별도 대본 유형 관리 시스템은 추가하지 않는다. 영어 발화 토큰(숫자·약어 발음 포함), 채널 발화 속도와 쉼을 바탕으로 40~60초 목표와 Hook 시간을 추정한다.
- 생성 결과와 별도로 검수 결과를 작성한다. 지적에는 심각도(`BLOCK` 또는 `RECOMMENDATION`), 위치, 관련 주장·출처 또는 비교 대상, 문제와 개선 방향을 남긴다. 허위 출처, 중요 사실 오류, 가설의 사실 단정, 실질적 반복, 필수 구조 오류(예: 세그먼트 누락, 잘못된 주장 참조)는 차단한다. Hook·결말·재미·스토리텔링의 경미한 부족은 개선 권고다. 공통 브랜딩만으로 차단하지 않는다. 예상 길이의 작은 편차는 발화 속도와 쉼 조정으로 보정할 수 있는지 평가하고 보정 가능한 경우 권고로 남긴다. 실제 음성 길이는 V2-04에서 확인한다.
- V2-03 로컬 검수기는 구조·참조·시간과 결정론적 fixture 판정을 검증한다. 차단 사유가 없는 대본은 권고를 보존하고 사용자 승인 없이 SCENES로 진행한다. 기존 실패 상태에 차단 이유를 남기며 별도의 필수 사용자 검수 대기 상태를 추가하지 않는다. 실제 의미 검수는 V2-05의 승인된 검수 경계에서 대상 해시에 연결된 독립 판정으로 검증한다. 지적 수정은 결함 fixture와 수정 fixture를 별도 입력으로 재검증한다.

### SCENES — R05

- 입력: 필수 차단 없이 검수를 마친 SCRIPT 해시와 세그먼트, 추정 발화 길이, 공통 스타일. 출력: `visualStyle`과 `scenes[{id, order, segmentIds, estimatedDurationMs, narration, visualDescription, imagePrompt, direction, transition, subtitleText}]`. 기존 시각 필드로 주요 피사체·배경·구도·카메라 시점·조명·움직임·공통 스타일과 9:16 가독성을 표현한다. 가상 장면은 관측 증거로 오인할 화면·문구를 피한다. 별도 연출 테이블과 타임라인 모델은 추가하지 않는다.
- 장면별 시간을 양의 밀리초로 제안하고 합계가 대본 추정 길이와 맞도록 서버가 확인한다. 전환은 첫 구현에서 장면 시간 안에 포함한다. 장면 개수는 내용과 시각적 변화에 맞춘다. 응답 크기·개수의 운영 상한만 둔다.
- 세그먼트는 대본 순서대로 한 번씩 포함한다. 내레이션과 자막 원문은 같은 세그먼트 텍스트에서 서버가 도출한다. 장면별 시각 설명은 대본에 없는 새 사실을 시청자에게 단정하지 않는다. V2-04에는 장면 ID·순서·추정 시간·내레이션·프롬프트·자막 원문 및 입력 해시를 넘긴다.

## 4. 저장 모델과 Migration — R06

기존 키와 참조를 유지하고 불변 단계 결과용 테이블 하나를 추가한다(R06 승인, 권장명 `production_stage_result`). V9의 `production_step.result_ref`는 참조를 담고 V10 본문은 DISCOVER에 사용한다. Revision은 실행 입력으로 유지한다. 작은 구조화 JSON은 DB에 보관해 본문·정산 증거를 원자적으로 저장하고 상세 조회와 복구에 사용한다. 향후 미디어 파일은 기존 workspace 설계를 따른다.

| 제안 필드 | 목적 |
|---|---|
| `operation_id` PK, `request_id`, `step_id` | 호출별 불변 결과, 해당 operation의 요청·단계와 일치 강제. 기존 복합 step FK 활용. operation 연결/소유권은 동일 잠금 트랜잭션에서 확인한다. |
| `schema_version`, `input_hash`, `input_json` | 변경되는 비교 자료와 검증 스냅샷 등 실제 발송 입력을 dispatch 전에 고정한다. 기존 영속 참조로 복원 가능한 큰 본문은 해시와 참조만 보관한다. |
| `body_json`, `body_hash`, `created_at` | 형식이 검증된 결과를 정규 JSON·SHA-256과 함께 최초 1회 저장한다. 응답 대기 또는 미실행은 본문이 비어 있다. |
| `validation_json` | 응답·입력 해시에 결합한 적용 검수 결과. fenced 트랜잭션에서 최초 1회 저장하며 차단과 개선 권고를 구분한다. |

결과 계보는 요청의 Run 및 단계 FK로 찾는다. 성공 단계만 후속 입력으로 소비한다. 차단된 검수 결과도 적용 영수증에 연결해 읽기 전용으로 노출한다. 중복 저장은 동일 해시만 허용한다. 신규 migration 번호와 파이프라인 버전은 최종 V2-02 병합 기준에서 확정한다. V1~V11과 과거 요청 계약은 유지하고 backfill 없이 진행한다. 기존 요청은 생성 당시 경로로 실행하며 신규 요청에 새 버전을 부여한다. 참조만 있는 행은 상세에서 본문 없음으로 표시한다.

## 5. 공급자 계약과 비용·복구

- 세 단계용 타입 입력·출력과 버전 검증기를 두고 V2-02의 타입 어댑터 패턴을 재사용한다. 공통 비용 서비스에 타입 단계 입력 및 응답 저장 훅을 연결한다. 실행기가 공급자를 직접 호출하지 않는다. 모델·가격·SDK는 실제 연동 승인 직전에 공식 문서에서 확인한다.
- 최소 조사 연결은 `retrieve(question, boundedQueries) → retrievedDocuments`, `verify(claim, documentRefs) → evidenceDecisions`이다. 출처 ID·조회 시각·발행 주체·문서 지문과 별도의 지지/반대/부족 판정을 받으며 모델은 서버가 발급한 참조만 선택한다. V2-03은 타입 계약, 조회·검증 경계, 오프라인 fixture, 비용 보호·복구를 구현한다. V2-05에서 별도 승인 후 실제 유료 검색·AI·의미 검증을 연결한다. 실제 조회에는 타임아웃·크기·리디렉션 제한과 로컬/사설 주소 차단을 적용하고 문서 본문은 자료로 취급한다. 각 과금 검색·생성·검증에는 기존 비용 포트의 별도 논리 효과를 사용하고 모두 같은 요청 한도에 귀속시킨다.
- FAKE는 서로 다른 IFNOVA 소재, 검증 부족, 허위 URL, 중복 대본, 장면 연결 오류를 결정적으로 재현한다. `origin=FAKE`와 `status=FIXTURE` 또는 `UNVERIFIED`를 서버가 지정한다. 테스트 모드에서만 fixture 근거로 성공 경로를 실행한다. 실제 조회가 필요한 인수 항목은 별도 승인된 어댑터 검증 전까지 미충족이다. 기존 후속 FAKE 단계로 이어지는 전체 회귀는 실제 영상 완성을 뜻하지 않는다.
- 기존 효과 키 생성 규칙인 요청·단계·대상·입력 세대를 유지한다. 정규 입력 해시가 다르면 동일 키 재발송을 거부한다. 기존 회계의 시스템/채널/요청 제한, 지출 차단, 예약 및 단일 dispatch 허가를 통과한 이후 DB 트랜잭션 밖에서 호출한다. 동일 요청으로 DISCOVER부터 QC까지 예산을 연결한다.
- 외부 응답의 구조·크기 검증 후 정규 본문과 정산 증거를 같은 DB 트랜잭션에 기록한다. 정산 커밋과 영수증 적용 사이에 종료되면 저장 증거와 본문을 재생한다. 소유권, 효과 키·입력 지문, 영수증 outcome·결과 참조·해시를 대조한다. 현재 lease의 fenced 트랜잭션에서 검수 기록, 단계 상태·결과 참조 및 영수증 적용을 함께 커밋한다. 본문 불일치·손상은 후속 진행을 차단하고 원인 확인 대상으로 남긴다.
- 호출 후 형식 오류 및 확정 비용은 기존 `EXECUTED_FAILED`로 정산한다. 형식은 유효하지만 필수 차단 조건을 위반한 본문은 정산하고 명시적 단계 오류와 검수 지적을 보존한다. 두 경우 모두 자동 재생성하지 않는다. 발송 후 타임아웃·응답 유실은 비용 불명 격리로 처리하며 미실행 증거가 나올 때까지 예약을 임의 해제하거나 재호출하지 않는다. 재조정에서 결과 채택은 확인한 본문과 증거가 함께 있어야 한다. 호출 전 실패와 확정 미실행만 기존 시도 한도·backoff·회수 규칙을 따른다. 취소는 추가 발송을 중단하고 이미 발생한 정산과 증거 적용을 보존한다.

## 6. API·화면과 예상 파일 범위 — R07

상세 조회와 같은 인증·요청자 범위를 사용한다. `GET /api/v1/production-requests/{id}/planning`은 적용된 단계 본문과 검수 지적을 반환한다. 폴링으로 함께 조회할 데이터는 크기를 제한한다. 미적용 영수증, 정산 증거 원문, 내부 프롬프트와 자격증명은 반환 대상에서 제외한다. 확인된 출처만 안전한 HTTP(S) 링크로 렌더링하고 확인 시각과 분류를 표시한다. 응답의 실행 방식과 출처 분류로 FAKE 실행과 실제 제작을 구분하고, 미검증·FIXTURE·FAKE를 화면에 명시한다. 실제 공급자 연결 전 V2-02의 고정 FAKE 완료 문구를 실행 방식에 따른 표시로 전환한다.

## 8. 위험과 검토 결정

- V2-02 독립 리뷰 P2에 따라 구조화된 주장 목록에서 누락되거나 정규식 밖에 있는 단정도 검수 대상으로 삼는다. V2-03 fixture에 제목·구성·내레이션에만 나타난 중요 사실 단정(숫자 없는 인과·비교 포함), 근거 연결 누락, 가설의 사실 단정을 포함한다. 로컬 검증은 알려진 사례와 인계·차단 경로를 검증하며 일반 텍스트의 탐지 완전성은 미검증으로 기록한다.
- V2-02의 어휘 기반 유사도는 의미상 중복을 놓칠 수 있다. V2-03에서는 표현이 다른 같은 질문·관점·설명·전개와, 어휘는 유사하지만 설명 가치가 다른 대본을 fixture로 비교한다. V2-05 실제 공급자 활성화 전에는 사람이 판정한 표본에서 누락된 중요 사실 주장, 실제 문서 조회와 주장 지지의 구분(반대·불충분 포함), 의미상 중복과 독립 가치의 판별을 검증한다. 공급자·판정 기준·비용 상한 및 결과 불명 복구 계약을 승인받고 차단·권고 결과를 확인한 뒤 활성화한다.
- 부분 실패·롤백 때 입력을 다시 조립하면 효과 키와 요청 해시가 어긋난다. 최초 발송 입력 고정, 원자 본문/증거 저장, 적용 시 계보 검증을 구현 독립 리뷰의 필수 항목으로 둔다.
- 통합 기준에서 V12, `production_stage_result`, `v2-planning-1`을 확정했다. SELECT의 Run/Revision과 요청 생성 시 고정된 불변 `channel_config`의 전략·시청자·내레이션·시각 스타일을 사용한다. 단계 본문을 UTF-8 128KiB로 제한하고 같은 채널의 최근 채택 대본 최대 20개를 고정한다. 예상 발화 40~60초는 정상, 35초 이상 40초 미만 및 60초 초과 65초 이하는 보정 권고, 그 밖은 차단이다. 길이를 맞추기 위한 불필요한 문장 추가를 피한다.
- 결과 조회는 제작 상세에서 요청하는 `GET /api/v1/production-requests/{id}/planning`으로 분리한다. 공통 단계는 기존 executor가 새 요청을 집지 않도록 신규 버전 선택을 기본 비활성 설정으로 둔다. V2-02 P3에 따라 조회 결과에 FAKE 실행 방식을 명시한다.
- 실제 공급자·의미 검수의 허용 기준 및 P3의 실제 제작 표시는 V2-05의 공급자 활성화 전에 검증한다.

Claude는 공급자 호출 없이 `PlanningExecutionPort`로만 실행하고, adopted 영수증의 본문 검수와 단계 상태 갱신을 한 fenced 트랜잭션에서 적용한다. 발화 경계·권고만 있는 대본의 진행·상반된 과학 소재 2개·P2 주장 누락 및 의미상 중복 fixture·장면 내용/시간/원문 검사를 포함한다. UI는 조회 API로 차단과 권고, FAKE와 FIXTURE를 표시한다. 독립 리뷰는 구현 세션과 분리한다.

변경 산출물은 이 파일 한 개다. 병렬 설계 worktree의 기록을 이 절에 두며 STATE.md 공통 갱신은 통합 담당자에게 맡긴다. 브랜치 및 기준 SHA는 문서 상단과 같다. 제품 테스트·CI는 실행하지 않았다. DB 조회·migration 적용·실제 유료 호출·게시를 수행하지 않았다. V2-02 최종 독립 검증, 실제 조회/검수 공급자, 구현 기준과 착수는 위 선행 조건을 따른다.
